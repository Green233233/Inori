# v0.6.0 功耗与后台驻留说明

本文记录「祈」v0.6.0 在**受控端（小狗端）**的功耗设计、实测口径与已知取舍。
主人端没有前台服务，只有前台页面里的短请求，因此不在本文重点。

## 1. 为什么受控端需要常驻

受控端要能接收主人的命令（查看屏幕时间、截屏、全屏消息、定位等），必须有一条
可被唤醒的连接。方案取舍：

| 方案 | 结论 |
|---|---|
| FCM 推送 | 依赖 Google 服务，国内机型不可用；且推送会带回 IP/设备标识 |
| 自建长连接（本版） | 一条 HTTP 长轮询，25 s 一次，服务器 hold 住请求；实现简单、可自托管 |
| 本地定时轮询 | 每次唤醒都要建连，息屏后耗电显著，已弃用 |
| 常驻 WebSocket | 需要额外心跳包与重连逻辑，收益有限，留待后续 |

**本版选择：单条 HTTP 长轮询，运行在唯一常驻前台服务 `PuppyGuardService` 中。**

## 2. 三档功耗模型

| 档位 | 前台轮询 | 息屏 | 息屏且 10 分钟无交互 | 充电时 | 适用场景 |
|---|---|---|---|---|---|
| 省电 SAVER | 60 s | 300 s | 600 s | 60 s | 只偶尔看看 |
| 智能 BALANCED（默认） | 25 s | 120 s | 300 s | 60 s | 日常 |
| 实时 REALTIME | 25 s | 25 s | 25 s | 25 s | 需要即时响应，2 小时后自动回落 |

- 低电量（<15% 且未充电）自动降级到 SAVER，并在恢复后回到用户选择。
- 档位由用户在小狗端「响应配置 → 连接频率」修改，主人端只能读取，不能强制。
- 长轮询在服务器端最多 hold 25 s；客户端一次请求失败退避 6 s，不做指数轰炸。

## 3. 明确的“不做”

- **不持有 WakeLock**（`grep WakeLock` 只有注释与文档，无 `PARTIAL_WAKE_LOCK` 申请）
- **不使用 `setInterval` / JS 定时器**：轮询循环是 `while` + 服务器 hold，不额外唤醒 CPU
- **不使用 AlarmManager 高频调度**：`AlarmManager` 只出现在 `canScheduleExactAlarms()` 查询里
- **不做后台截屏/录屏**：截屏必须是主人当次请求 + 小狗端授权（API 34+ 逐次确认）
- **不做后台定位轮转**：定位默认 `PASSIVE_PROVIDER` 复用，网络定位 30 分钟闸门且默认关闭
- **不做后台使用统计扫描**：`UsageStats` 只在主人请求或小狗打开页面时查询一次

## 4. 事件驱动而非轮询

| 能力 | 触发方式 |
|---|---|
| 屏幕开关状态 | `ACTION_SCREEN_ON/OFF`、`ACTION_USER_PRESENT` 广播，写入内存状态 |
| 通知转发 | `NotificationListenerService` 回调，只在白名单命中时入队 |
| 开机/更新补同步 | `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` 一次性标记，不常驻 |
| 网络恢复 | 守护服务内动态注册 `CONNECTIVITY_CHANGE`，只在服务运行时生效 |

## 5. 实测口径（复现命令）

> 模拟器无法代表真实 mAh，以下只验证「唤醒次数 / CPU / JS 定时器」三类结构性指标。

```bash
# 1) 唤醒与闹钟（2 小时息屏后）
adb shell dumpsys alarm | grep -A3 com.green.inorinal
adb shell dumpsys deviceidle | grep -i inorinal

# 2) CPU 占用（连续采样）
adb shell top -n 20 -d 5 | grep inorinal

# 3) 网络唤醒
adb shell dumpsys netstats detail | grep -A5 com.green.inorinal

# 4) JS 定时器（应无定时器）
#   代码层检查：grep -rn "setInterval" react-native/src
#   运行时：React DevTools / Hermes profiler 仍可见 pending timers
```

### v0.6.0 验收目标（结构指标，实测记录见 regression 文档）
### 2026-11-18 实测记录（emulator-5556，release 包）

- `dumpsys power` 的 Wake Locks 段 `size=2`，两条都是 Firebase 的 `fiid-sync`；**本应用 uid 未持有任何 wake lock**。
- 代码审阅：`src` 下唯一的 `setInterval` 是绑定页等待对方加入时的 2.5 s 轮询（仅在绑定页前台、卸载即 `clearInterval`），其余全部为事件驱动；`ImageViewer` 的 50 ms 引导轮询上限 4 s、页面关闭即止。因此「后台常驻期间的 JS 周期定时器 = 0」仍成立，前台短时轮询已在文档中显式列为例外。
- 用量顶部列表由 Kotlin 侧 `PackageManager.getApplicationLabel()` 解析应用名（缓存），失败才回退包名，避免主人端看到 `nexusmart-launcher` 这类内部包名。


- 息屏 2 小时：SAVER ≤ 15 次唤醒/小时、BALANCED ≤ 60 次/小时
- 应用自身 WakeLock：**0**
- JS 周期定时器：**0**
- 息屏期间无截屏、无定位、无使用统计查询

## 6. 已知取舍

1. **App 被杀后不自动复活**：没有 `JobScheduler`/`WorkManager` 保活，用户手动打开才会恢复守护。
   这是刻意的：对抗系统省电策略的保活会显著增加耗电，也容易被判定为恶意软件。
2. **网络中断期间命令丢失**：长轮询失败只做 6 s 退避重试，不做离线队列；主人端会看到明确超时。
3. **REALTIME 有时限**：连续 2 小时自动回落到 BALANCED，避免长期高频唤醒。
4. **模拟器 measurements 仅作结构性验证**，真实续航需在实体机上用 `Battery Historian` 复测。

## 7. 后续可优化项

- 用服务器 `wait` 参数自适应（当前固定 25 s）随档位下发
- 息屏时把多次轮询合并为一次（服务器侧 hold 更久）
- 小组件刷新与长轮询合并，避免额外唤醒
