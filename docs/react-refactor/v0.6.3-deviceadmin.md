# v0.6.3 设备管理员（DeviceAdmin）能力核实与保活结论

- 核实对象：`com.green.inorinal`（namespace `com.inorinal`）v0.6.2，分支 `react`
- 核实方式：静态阅读当前 APK 源码 + AOSP 策略常量清单 + 两台 Android 15（API 35）模拟器只读观察
- 本文只读：**没有**激活/撤销任何设备管理员，也没有改动设备或代码
- 凡未在真机/模拟器上实际执行的操作，均标注「待实测」
- 行号快照：文中 `文件:行号` 取自 2026-11-19 的只读工作区快照。核实期间该工作区正被并发重构（`PermissionCenterModule.kt`、`PuppyGuardService.kt`、`QiLinkService.kt`、`QiDevice.ts`、`src/sync/commands.ts` 等均为未提交的 `M` 状态），行号可能继续漂移；**当函数名/常量名仍在而行号对不上时，请以锚点 grep 为准**（如 `settingsIntent`、`revoke`、`deviceAdminActive`、`lockNow`、`baselineType`、`relayLoop`、`backoffMs`）

## 一、结论摘要

1. **不能保活。** DeviceAdmin 是「设备策略」授权，不是「进程存活」授权；AOSP 的策略集合（`DeviceAdminInfo.USES_POLICY_*` 共 10 个）里没有任何一项与进程、服务、唤醒锁、Doze 白名单或后台启动豁免有关。
2. 本 APK 只申请了一条策略：`force-lock`（`react-native/android/app/src/main/res/xml/device_admin.xml:8-10`），它唯一对应的能力是 `DevicePolicyManager.lockNow()` 与 `setMaximumTimeToLock()`。
3. 激活/撤销链路是**完整可用**的：`ACTION_ADD_DEVICE_ADMIN` + `EXTRA_DEVICE_ADMIN` + `EXTRA_ADD_EXPLANATION`、`isAdminActive()`、`ACTION_REMOVE_DEVICE_ADMIN` 都在（`PermissionCenterModule.kt:295-300`、`:193-199`、`:133-165`）。
4. 但「申请了」≠「已利用」：`lockNow()` 只在 `GuardModule.kt:183-199` 暴露为原生 API，**JS 侧没有任何页面或 relay 命令调用它**（`src/native/QiDevice.ts` 里只有 `lockNow: (): Promise<boolean> => requireGuard().lockNow()` 这一层包装）。即当前设备管理员处于「申请了、能锁屏、但没人用」的状态。
5. 当前真正的保活链路是前台服务 + 常驻通知 + 自适应轮询（`PuppyGuardService` / `QiLinkService`），与 DeviceAdmin 完全无关；只读观察时小狗端 `PuppyGuardService` 已连续前台运行 25 分 19 秒（`createdFromFg=true`），而此时 `enabled_device_admins` 为 `null`——**不激活设备管理员，守护服务照样活着**。
6. 「设备管理员能保活」的传闻来自三处误读：OEM 省电白名单把「已激活管理员」当可信信号（不可编程、各 ROM 不同）；企业 MDM 的能力其实来自 **Device Owner**（需恢复出厂或 adb provision，已用设备拿不到）；无障碍服务被误认成设备管理员。
7. 想让小狗端更抗杀，正确方向是前台服务类型选对 + 引导用户关闭电池优化 + 精确闹钟/WorkManager 做兜底，而不是加设备管理员策略。
8. 建议：保留 `force-lock` 作为「主人同意后远程锁屏」的能力没问题，但要么补一个显式入口，要么在文档/UI 里说清它是**按需锁屏**而非保活——现状的「已授权 7/10」容易让人误以为它参与了守护。

## 三、激活与撤销流程

### 3.1 激活（用户主动 → 系统页 → 回读）

```
PermissionCenter.tsx:164-174  「去设置」按钮
        │  qiDevicePermissions.openSettings('deviceAdmin')
        ▼
PermissionCenterModule.settingsIntent()            :295-300
        │  Intent(ACTION_ADD_DEVICE_ADMIN)
        │    .putExtra(EXTRA_DEVICE_ADMIN, ComponentName(com.green.inorinal, com.inorinal.qi.QiDeviceAdminReceiver))
        │    .putExtra(EXTRA_ADD_EXPLANATION, "允许祈在你同意时锁定屏幕（仅此一项）")
        ▼
系统 DeviceAdminAdd 页面（com.android.settings，进程外，本应用无法定制）
        │  用户点「激活」
        ▼
QiDeviceAdminReceiver.onEnabled()（未覆写，空实现）
        ▼
isAdminActive() == true → PermissionCenter 重新 snapshot → Pill 变「已授权」
```

用户会看到什么：
- 这是**系统页面**，不是应用内弹窗。页面会列出该 admin 申请的策略及说明。`force-lock` 的文案来自 AOSP internal 资源 `policylab_forceLock` / `policydesc_forceLock`（中文系统上大意是「锁定屏幕」/「允许管理员锁定屏幕」）；确认按钮为「激活」、取消为「取消」。
- `EXTRA_ADD_EXPLANATION` 的「允许祈在你同意时锁定屏幕（仅此一项）」会作为补充说明显示在页面上。
- **具体字符串随系统版本、语言与 ROM 变化，本文不引用未经实测的原文字面**，标注「待实测」记录（见 §7 检查 ①）。
- Android 11+ 的系统页会显示应用名与图标（来自 Manifest 的 `android:label` / `android:icon`）。

### 3.2 撤销（用户主动 → 系统页 → 回读）

```
PermissionCenter 撤销按钮
        │  qiDevicePermissions.revoke('deviceAdmin')
        ▼
PermissionCenterModule.revoke()                     :133-165
        │  Intent("android.app.action.REMOVE_DEVICE_ADMIN")   // :140-143 说明：平台只暴露了 ADD 的常量
        │    .putExtra(EXTRA_DEVICE_ADMIN, …)
        │    .putExtra(EXTRA_ADD_EXPLANATION, "移除后祈将无法再锁定屏幕")   // :145-148
        ▼
系统「解除激活」确认页 → 用户确认
        ▼
QiDeviceAdminReceiver.onDisabled()（未覆写）
        ▼
isAdminActive() == false
```

关键点：`revoke()` **不会**直接改状态，只能拉起系统页让用户确认，因此实现诚实地返回：

```kotlin
// PermissionCenterModule.kt:153-155
result.putBoolean("revoked", false)          // 永远 false，因为要用户手动确认
result.putBoolean("launched", launched)      // 是否成功拉起系统页
result.putBoolean("needsUserAction", true)
```

JS 类型注释也写明 `revoked: Always false today`（`react-native/src/native/QiDevice.ts:55-61`，`PermissionRevokeResult`）。要判断「是否真的撤销了」，只能重新 `status('deviceAdmin')` 读 `isAdminActive`。

### 3.3 「申请了但拿不到」的边界情况

| 情况 | 会发生什么 | 依据 |
| --- | --- | --- |
| 用户在系统页点「取消」 | `isAdminActive` 仍为 `false`，不会报错；UI 停留在「未授权」 | `PermissionCenterModule.kt:193-199` 返回 false |
| 系统页根本没弹出来（`startActivity` 抛异常） | `launched=false`、`needsUserAction=true`，调用方需提示用户 | `:133-165` 的 `launched` 语义 |
| 设备没有 `FEATURE_DEVICE_ADMIN`（部分 headless / automotive / 企业定制 ROM） | `dpm` 为 null 或 `isAdminActive` 抛异常 → `getOrDefault(false)` 吞掉，永远拿不到；`mHasFeature=false` | `dumpsys device_policy` 的 `Immutable state: mHasFeature=…`；本机实测 `mHasFeature=true` |
| 已有其他设备管理员 | **不冲突**：Android 支持多个 active admin 共存，我们仍可被添加 | AOSP `DevicePolicyManager` 允许多 admin；`enabled_device_admins` 是列表 |
| 设备已被 Device Owner / Profile Owner 管理（企业 MDM、公司手机） | 组织策略可能禁止添加管理员或禁止 `force-lock`（`setDeviceAdminFeatures` / `DISALLOW_*` 一类限制由 DPC 下发）；此时系统页会拒绝或策略不生效 | 需按具体 DPC 策略判断，标注「待实测（仅企业设备场景）」 |
| 设备被 root / `dpm` 命令被裁掉 | 用户态调用仍走 `DevicePolicyManager` 服务，通常可用；但 adb 侧的 `dpm` 子命令可能被裁（见 §7：Android 15 的 `dpm list owners` 已不存在） | 本机实测 `dpm` usage 只有 `list-owners` |
| 应用被卸载 / 清数据 | admin 自动移除 | 系统行为，`enabled_device_admins` 变空 |
| 想用 `adb shell dpm remove-active-admin` 强删 | 要求 APK 声明 `android:testOnly="true"`，release 包不满足 | `dpm` usage 原文：`the admin must have declared android:testOnly in the application in its manifest` |

结论：普通用户设备上，「激活」这一步的成功率只取决于用户在系统页点没点「激活」，没有隐蔽的权限门槛；失败面主要是企业托管设备与定制 ROM。

## 四、为什么 DeviceAdmin 不能保活（AOSP 依据逐条）

### 4.1 策略枚举是封闭的，且里面没有「进程」

AOSP `core/java/android/app/admin/DeviceAdminInfo.java` 定义了全部可用策略，一共 10 个（`sKnownPolicies` / `sPoliciesDisplayOrder` 的映射即 XML 标签白名单）：

| 常量 | 值 | XML 标签 | 实际能力 | 与保活有关？ |
| --- | --- | --- | --- | --- |
| `USES_POLICY_LIMIT_PASSWORD` | 0 | `limit-password` | 密码质量/长度（**需 device owner 或 profile owner**） | 否 |
| `USES_POLICY_WATCH_LOGIN` | 1 | `watch-login` | 观察解锁失败/成功、`getCurrentFailedPasswordAttempts()` | 否 |
| `USES_POLICY_RESET_PASSWORD` | 2 | `reset-password` | 重设密码（旧 API，现代设备基本不可用） | 否 |
| `USES_POLICY_FORCE_LOCK` | 3 | `force-lock` | `lockNow()`、`setMaximumTimeToLock()` | 否 |
| `USES_POLICY_WIPE_DATA` | 4 | `wipe-data` | `wipeData()` 恢复出厂（现代设备需 DO/PO 才真正生效） | 否 |
| `USES_POLICY_SETS_GLOBAL_PROXY` | 5 | `set-global-proxy`（`@hide`） | 全局 HTTP 代理 | 否 |
| `USES_POLICY_EXPIRE_PASSWORD` | 6 | `expire-password` | 密码过期（**需 DO/PO**） | 否 |
| `USES_ENCRYPTED_STORAGE` | 7 | `encrypted-storage` | 要求存储加密（历史遗留） | 否 |
| `USES_POLICY_DISABLE_CAMERA` | 8 | `disable-camera` | 禁用相机（**需 DO/PO**） | 否 |
| `USES_POLICY_DISABLE_KEYGUARD_FEATURES` | 9 | `disable-keyguard-features` | 禁用锁屏特性如指纹/通知（**需 DO/PO**） | 否 |

**依据名：`DeviceAdminInfo.USES_POLICY_*`（10 个常量即全集）。** 清单里没有任何 `KEEP_ALIVE`、`RUN_IN_BACKGROUND`、`WAKE_LOCK`、`BATTERY_EXEMPT` 之类的项——加不存在的标签只会得到一条 `Unknown tag under uses-policies` 警告（`DeviceAdminInfo` 解析逻辑原文：`Log.w(TAG, "Unknown tag under uses-policies of " + getComponent() + ": " + policyName)`），不会获得任何能力。

### 4.2 每一条策略的 Javadoc 都指向设备策略，没有进程语义

- **`force-lock`** → Javadoc 原文只列 `DevicePolicyManager#lockNow` 与 `#setMaximumTimeToLock`。本项目用的就是前者（`GuardModule.kt:193`）。它让屏幕立刻锁上，**不改变任何进程的优先级**。
- **`wipe-data`** → `DevicePolicyManager#wipeData`。这是「删数据」，与「让进程活着」是相反方向。
- **`disable-camera` / `disable-keyguard-features` / `limit-password` / `expire-password`** → Javadoc 明确写 `the device admin must be a device owner or profile owner`。也就是说，**普通用户手动激活的 admin 连这几项都拿不到**，更谈不上拿它们保活。
- **`disable-keyguard-features` 特别澄清**：名字里有「keyguard」，但它禁用/启用的是**锁屏上的功能**（指纹解锁、通知、快捷方式、相机等，见 `DevicePolicyManager#setKeyguardDisabledFeatures`），既不阻止屏幕休眠，也不让进程常驻；而且它要求 DO/PO。把它当成「保持唤醒」是常见误读。
- **`watch-login`**：只让 admin 收到 `ACTION_PASSWORD_FAILED` / `ACTION_PASSWORD_SUCCEEDED` 并读失败次数，是事件通知，不是进程控制。
- **`set-global-proxy`** → `@hide`，第三方应用无法在 XML 里正常使用。

**依据名：`DeviceAdminInfo` 各常量的 Javadoc；`DevicePolicyManager#lockNow` / `#wipeData` / `#setMaximumTimeToLock`。**

### 4.3 「安装/卸载应用」不是 DeviceAdmin 策略

AOSP 的 `uses-policies` 白名单里**没有** `install-packages` / `uninstall-packages` 标签（`sKnownPolicies` 只有上表 10 项）。安装/卸载控制属于 **Device Owner** 的能力：

- `DevicePolicyManager#setUninstallBlocked(ComponentName, String, boolean)` —— 阻止卸载指定包；
- `DevicePolicyManager#setPackagesSuspended(ComponentName, String[], boolean)` —— 挂起应用；
- `DevicePolicyManager#installExistingPackage` / `setPermissionGrantState` 等也要求 DO/PO。

**依据名：`DeviceAdminInfo.sKnownPolicies`（无该标签）；`DevicePolicyManager#setUninstallBlocked` / `#setPackagesSuspended`（要求 DO/PO）。**

### 4.4 `DevicePolicyManager` 里根本没有「让某进程常驻」的 API

`DevicePolicyManager` 的公开方法与存活有关的一个都没有：
- 没有 start/bind service、没有设置进程重要性、没有 `oom_adj` / `oom_score_adj` 调整；
- 没有唤醒锁（WakeLock 属于 `PowerManager`，且 Doze 下普通 wakelock 也会被压制）；
- 没有 Doze/App Standby 白名单入口——白名单 API 在 **`PowerManager#isIgnoringBatteryOptimizations`** + `Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，判定依据是「用户是否对本包点了允许」，**不看是否 device admin**；
- 没有「后台启动豁免」——`startForegroundService` 的后台限制豁免清单由系统维护（`BOOT_COMPLETED`、高优先级 FCM、`SYSTEM_ALERT_WINDOW` 等特定场景），**没有 device admin 条目**。

**依据名：`DevicePolicyManager` 公开方法集合；`PowerManager#isIgnoringBatteryOptimizations`；`Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`；`Context#startForegroundService` 的后台启动限制豁免规则。**

### 4.5 前台服务类型与 DeviceAdmin 无关

前台服务是否「合法常驻」由 **`ServiceInfo.FOREGROUND_SERVICE_TYPE_*`** + Manifest 的 `android:foregroundServiceType` + 对应权限（`FOREGROUND_SERVICE_SPECIAL_USE` 等）决定。本项目用的是 `specialUse|mediaProjection`（`AndroidManifest.xml:66-75`），并在 `PuppyGuardService.kt:297-298` 按 SDK 选择 `FOREGROUND_SERVICE_TYPE_SPECIAL_USE`。这条链路上的每个决策都跟 admin 状态无关。

**依据名：`ServiceInfo.FOREGROUND_SERVICE_TYPE_SPECIAL_USE` / `_MEDIA_PROJECTION`；`Service.startForeground(int, Notification, int)`。**

### 4.6 进程优先级由 AMS 按组件状态算，admin 不是一种组件状态

`ActivityManagerService` 计算 `oom_adj` 时看的是：是否有前台 Activity、是否有前台服务、是否有可见服务、是否有绑定、是否在 recent 列表、进程是否为空等。**「这个包是 active device admin」不是输入项**——`dumpsys activity processes` 的 `ProcessRecord` 里也没有 admin 相关字段，只有 `ServiceRecord` 的 `isForeground` / `foregroundId`。

**依据名：`ActivityManagerService` 的 `computeOomAdjLocked` 输入集合；`dumpsys activity processes` 的 `ProcessRecord` 字段。**

### 4.7 反向证据（实测）

本次在小狗端模拟器（`emulator-5556`）只读观察到：

```
Enabled Device Admins (User 0, provisioningState: 0):     ← 空
settings get secure enabled_device_admins → null
```

而同一时刻守护服务活着：

```
* ServiceRecord{516fca u0 com.green.inorinal/com.inorinal.qi.PuppyGuardService}
    isForeground=true foregroundId=28929 types=0x40000000
    foregroundNoti=Notification(channel=qi.guard … flags=ONGOING_EVENT|ONLY_ALERT_ONCE|FOREGROUND_SERVICE …)
    lastActivity=-25m19s601ms restartTime=-25m19s601ms createdFromFg=true
    startRequested=true delayedStop=false stopIfKilled=false callStart=true
```

`types=0x40000000` 即 `FOREGROUND_SERVICE_TYPE_SPECIAL_USE`。**设备管理员未激活，前台服务照样连续跑了 25 分 19 秒**——这是「保活不依赖 DeviceAdmin」最直接的现场证据。

## 五、DeviceAdmin 的合理用途（本项目只用 lockNow）

### 5.1 本项目为什么需要它

产品语义是「小狗请求、主人同意后锁屏」。`lockNow()` 是**不申请无障碍的前提下**普通应用唯一能立即熄屏锁定的途径（`DevicePolicyManager#lockNow`；无障碍的 `GLOBAL_ACTION_LOCK_SCREEN` 也能锁屏，但那要读输入的权限，本项目明确不采用，见 §6 第 9 行），而它要求调用方是 active device admin——所以 `force-lock` 这一条策略是「锁屏」能力的许可证，属于最小必要授权。

`GuardModule.kt:179-180` 的注释与 `device_admin.xml:2-6` 的注释都明确写了边界：不做 wipe、不做密码策略、不做 keyguard reset、不做静默安装。

### 5.2 边界

| 能做 | 不能做 |
| --- | --- |
| 主动 `lockNow()` 锁屏 | 保活、拉起进程、豁免 Doze、绕过后台启动限制 |
| `setMaximumTimeToLock()` 限制最长解锁时间（需额外 UI，当前未接） | 抹除数据（未申请 `wipe-data`） |
| 观察自己的启用/禁用回调（当前未覆写） | 改密码、禁用相机、禁用锁屏特性（需 DO/PO，未申请） |
| — | 安装/卸载其他应用（平台无此策略） |

### 5.3 现状问题：能力悬空

- `lockNow()` 已有原生实现（`GuardModule.kt:183-199`）、已有 JS 包装（`src/native/QiDevice.ts` 的 `qiGuard.lockNow`，实现只有一句 `requireGuard().lockNow()`），但**全仓没有页面/命令调用点**：`src/sync/commands.ts` 只有 `guard.status` / `guard.tier`，`src` 下 grep「锁屏」0 命中。
- 后果 1：用户被要求激活一个「只用于锁屏」的权限，但当前版本没有任何路径会用到它——从最小权限原则看这是**可以砍掉**的授权。
- 后果 2：`QiDeviceAdminReceiver` 是空实现，没有 `onEnabled` / `onDisabled`，所以「用户悄悄去系统设置里撤销了」这件事**不会**产生本地审计记录，只能靠下次 `status()` 轮询发现。
- 后果 3：`revoke()` 返回 `revoked=false` 是诚实的，但如果 UI 把它当「已撤销」展示，就会与真实状态不一致（当前 UI 是重新 snapshot，问题不大）。

### 5.4 建议（不在本次改动范围）

1. 要么补一个显式入口（例如「和好券」之外的紧急动作、或 relay 的 `admin.lock` 命令），要么把 `deviceAdmin` 从 10 项权限里暂时移除，减少无效授权。
2. 若保留：在 `QiDeviceAdminReceiver` 里覆写 `onEnabled` / `onDisabled` 写 `AuditLogModule`，让撤销可追溯。
3. UI 文案建议从「仅用于锁定屏幕」再进一步，明确「它不能让祈在后台常驻」——避免用户以为激活了就「更不容易被杀」。

## 七、真机验证清单

> 全部命令只读（除 ② 需要在应用内点一下「锁屏」触发）。`$S` 为设备序列号，例如 `emulator-5556`（小狗端）。
> 观察环境：Windows + MSYS bash + `adb 1.0.41 (37.0.0-14910828)`。

### 检查 ①：设置里能看到并激活「祈」的设备管理员

```bash
# 1. 激活前：应为空
adb -s $S shell dumpsys device_policy | sed -n '/Enabled Device Admins/,/^$/p'

# 2. 手动激活：应用内「我的 → 权限中心 → 设备管理器 → 去设置 → 激活」

  -e android.app.extra.DEVICE_ADMIN com.green.inorinal/com.inorinal.qi.QiDeviceAdminReceiver \
  -e android.app.extra.ADD_EXPLANATION "允许祈在你同意时锁定屏幕（仅此一项）"

# 3. 激活后：应出现该组件
adb -s $S shell dumpsys device_policy | sed -n '/Enabled Device Admins/,/^$/p'
adb -s $S shell settings get secure enabled_device_admins
```

预期输出对照：

| 时点 | `dumpsys device_policy` 的 `Enabled Device Admins` 段 | `settings get secure enabled_device_admins` | `dpm list-owners` |
| --- | --- | --- | --- |
| 激活前（本机实测） | 段头之后为空 | `null` | `no owners` |
| 激活后（**已实测**） | 出现 `com.green.inorinal/com.inorinal.qi.QiDeviceAdminReceiver: uid=10211 testOnlyAdmin=false` | `0:com.green.inorinal/com.inorinal.qi.QiDeviceAdminReceiver` | 仍为 `no owners`（admin ≠ owner） |

注意事项（本机实测发现）：
- **组件名必须写全**：`com.green.inorinal/com.inorinal.qi.QiDeviceAdminReceiver`。Manifest 没有 `package=` 属性，命名空间是 `com.inorinal`，所以 `.qi.…` 这种相对写法会解析成不存在的 `com.green.inorinal.qi.QiDeviceAdminReceiver`，`am start -a android.app.action.ADD_DEVICE_ADMIN` 只会打印 `Starting: Intent {…}` 而**不弹任何页面**（本轮踩过，误以为功能坏了）。
- 本机可用 `adb shell dpm set-active-admin com.green.inorinal/com.inorinal.qi.QiDeviceAdminReceiver` 直接激活，输出 `Success: Active admin set to component …`；`install -r` 覆盖安装**不会**清除已激活的 admin。
- **`adb shell dpm list owners` 在 Android 15 上不存在**，会返回 `Unknown command: list` + usage。正确子命令是 **`dpm list-owners`**（带连字符）。
- `dpm remove-active-admin` 对非 testOnly 包会抛 `SecurityException: Attempt to remove non-test admin ComponentInfo{…}`，所以**不能用它撤销 release/debug 正式包**，撤销只能走应用内或系统设置。
- **Android 15 已移除撤销入口 activity**：`cmd package resolve-activity --brief -a android.app.action.REMOVE_DEVICE_ADMIN`、`android.settings.DEVICE_ADMIN_SETTINGS`、`android.app.action.DEVICE_ADMIN_SETTINGS` **全部 `No activity found`**（只有 `android.app.action.ADD_DEVICE_ADMIN → com.android.settings/.applications.specialaccess.deviceadmin.DeviceAdminAdd` 还在）。原先 `PermissionCenterModule.revoke()` 发 `REMOVE_DEVICE_ADMIN` 是静默无效，已改为直接调 `DevicePolicyManager.removeActiveAdmin(adminComponent)` 并返回 `revoked`，实测可撤销。
- 系统激活页的具体中文文案随 ROM 变化，本文不引用字面文案。

### 检查 ②：应用内 `lockNow()` 能锁屏


**已实测（v0.6.3 新增「远程锁屏」）**：主人端「设备管控中心 → 远程锁屏」→ 命令 `guard.lock` 经中继下发 → 小狗端常驻服务 `QiLinkService.lockDeviceNow()` 调 `lockNow()`。实测（小狗 `emulator-5554`，Android 15）：

注意（本机 API 35 实测）：**`mShowingLockscreen` 在 Android 15 已不存在**，`dumpsys window` 里可用的是 `isKeyguardShowing` 与 `mDreamingLockscreen`。任务里若写了 `mShowingLockscreen`，需按此替换。

### 检查 ③：撤销后 `lockNow()` 返回 `device_admin_missing`


| 检查项 | 预期 | 依据 |
| --- | --- | --- |
| `enabled_device_admins` | `null` | 系统设置，撤销后清空 |
| `lockNow()` 的 Promise reject | `code="device_admin_missing"`，`message="还需要开启设备管理员才能锁定屏幕"` | `GuardModule.kt:190` |

**已实测（v0.6.3）**：撤销链路已从「发 `ACTION_REMOVE_DEVICE_ADMIN`」改为直接调 `DevicePolicyManager.removeActiveAdmin()`（Android 15 三个候选 activity 全 `No activity found`）。撤销后 `enabled_device_admins` 回到 `null`、`Enabled Device Admins` 段清空。

## 八、A/B/C 保活对照实验方案

目的：用可复现的 30 分钟窗口，证明「激活 DeviceAdmin」对守护进程存活没有正向影响。

- **A 组（基线）**：仅前台服务 + 电池优化白名单（本项目现状）
- **B 组**：A + DeviceAdmin **已激活**
- **C 组**：A + DeviceAdmin **未激活**（与 A 相同配置，作为对照漂移检查；若 A 与 C 差异明显，说明测量噪声大，需重跑）

每组 30 分钟，组间至少留 5 分钟冷却。建议顺序：C → B → A（先测未激活，再激活测 B，最后撤销后复测 A，顺便验证撤销链路）。

### 8.1 每组开始前

```bash
S=emulator-5556   # 小狗端
PKG=com.green.inorinal

# 0) 固定条件：同一充电状态、同一亮度、同一网络
adb -s $S shell dumpsys battery | grep -E "level|status|powered"
adb -s $S shell settings get system screen_brightness_mode

# 1) 记录 admin 状态（B 组必须为已激活，C 组必须为 null）
adb -s $S shell settings get secure enabled_device_admins

# 2) 确认服务在跑
adb -s $S shell "dumpsys activity services $PKG" | grep -E "ServiceRecord|isForeground"

# 3) 清空事件日志（可选；会丢掉历史，仅实验用）
adb -s $S logcat -b events -c

# 4) 记录起点时间与电量
date +%H:%M:%S
adb -s $S shell dumpsys battery | grep level
```

### 8.2 30 分钟窗口内（每 5 分钟采一次，或只在 0/30 分钟采两次）

```bash
# 进程是否存活 + 是否被重建（PID / 启动时间会变）
adb -s $S shell "dumpsys activity processes | grep -A2 inorinal"

# 前台服务状态
adb -s $S shell "dumpsys activity services $PKG" | grep -E "isForeground|foregroundId|lastActivity"

# 进程启动次数（本包）
adb -s $S logcat -b events -d | grep am_proc_start | grep -c inorinal

# Doze / App Standby 状态
adb -s $S shell dumpsys deviceidle | grep -E "mState=|mLightState=|mScreenOn=|mCharging="
adb -s $S shell am get-standby-bucket $PKG     # 10=ACTIVE 20=WORKING_SET 30=FREQUENT 40=RARE 45=RESTRICTED 5=EXEMPTED

# 耗电归属
adb -s $S shell "dumpsys batterystats --charged $PKG" | head -40
```

### 8.3 结束时

```bash
date +%H:%M:%S
adb -s $S shell dumpsys battery | grep level
adb -s $S shell "dumpsys activity processes | grep -A2 inorinal"
adb -s $S logcat -b events -d | grep am_proc_start | grep inorinal
adb -s $S shell dumpsys deviceidle | grep -E "mState=|mLightState="
```

### 8.5 实验的合规边界

- B 组需要**手动激活**设备管理员（系统页点「激活」），这属于改设备状态，必须由用户/主代理在真机上做，`tools/verify-deviceadmin.sh` **不会**做。
- 撤销同样手动。实验结束后应恢复原状（未激活）。
- 不要把「通过 adb 强制 `dpm set-active-admin`」当作 B 组的建立方式——那是 adb 特权路径，与用户实际路径不同，会污染结论。

## 附：一句话回答用户

> 设备管理器可以正常申请、也能正常锁屏，但它**不能**保活：Android 官方给设备管理员的 10 条策略里没有一条与进程存活有关，真正的常驻能力来自前台服务 + 常驻通知 + 电池优化白名单（这些本项目已经在用）。当前代码里 `lockNow()` 甚至还没有调用入口，设备管理员处于「申请了但没被利用」的状态——要提升抗杀能力，应该补 OEM 自启动引导和兜底任务，而不是加设备管理员策略。
