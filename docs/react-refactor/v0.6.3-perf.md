# v0.6.3 性能排查

## 结论
- **冷启动**：debug APK 必须 `adb shell cmd package compile -m speed -f com.green.inorinal`（AOT），否则未 AOT 的 ART verify 会把启动拖过 AMS 超时（`failed to attach` → `start timeout`）。AOT 后本轮实测 `am start -W`：主人端 744ms / 2069ms，小狗端 408ms / 1255ms。发布版（release + R8）不受此影响。
- **使用数据聚合下沉原生**：`UsageStatsModule` 从 307 行扩到 892 行后，`dayStats / rangeStats(≤30) / sessions / installedApps` 全部在单线程 `qi-usage` 上跑，JS 只拿结构化结果。
  - `collectDays()` 只扫**一次** `queryEvents`，按天分桶，跨零点的会话两天各取自己那段；`MAX_SESSION_COUNT=2000` 上限、`addSession()` 6 小时截断，避免异常事件把内存打爆。
  - 应用列表 `TOP_APP_COUNT=12` 截断，但分类分钟数按**全部应用**累加，所以「未分类 44 分钟」不会因为 Top 12 之外的应用而失真。
  - 图标按包缓存，48dp 起、>8KB 逐级减半（最小 16px），产出 `data:image/png;base64,…`；不申请 `QUERY_ALL_PACKAGES`，只用 manifest 已有的 `<queries>` MAIN/LAUNCHER。
- **应用限制的检测成本**：`AppLimitWatcher` 用单线程 `ScheduledExecutorService`（daemon、`MIN_PRIORITY`），省电档 4000ms、其余 1500ms；每次只在 `now-10_000 .. now` 上做一次 `queryEvents`。只有「规则启用 + 名单非空 + 亮屏 + 未锁屏」才续约下一次，其余情况立刻取消 pending 并 `hide()`；灭屏/解锁由 `ACTION_SCREEN_OFF/ON`、`USER_PRESENT`（`RECEIVER_NOT_EXPORTED`）重排。**不起前台服务、不拿 WakeLock、不用 AlarmManager**。应用名只对命中包解析，`HashMap` 缓存上限 200，从不 `getInstalledPackages` 全量枚举；审计 `app.limit.block` 同包 60s 去抖。
- **常驻服务**：`QiLinkService` 仍 30s 长轮询 + 5/30/60s 退避。新增的 `app.limit` / `guard.lock` 复用同一次 poll 的 items，不额外起线程；原生执行完后 reply POST 成功才 ack（失败留待下一轮，避免丢规则）。
- **命令超时** 40s（小狗端 25s 长轮询 + 加解密余量）；`guard.lock` 实测从点击到小狗端屏幕熄灭 < 8s。
- **轨迹页**：`usage.sessions` 只取最后 300 段渲染，位置/出行来自本机 `files/qi/puppy-trail.json`（上限 200 点、同分钟去重），无网络请求。

## 已知代价
- 拦截浮层每 1.5 秒判定一次，最坏情况下被禁应用有 1 帧可见（约 16ms 量级，肉眼基本不可见；省电档最坏 4 秒）。进一步优化需要 `AccessibilityService` 事件驱动，本版按既定决策不引入。
- 使用时长页一次要打 3 个命令（`usage.day` 今天 + 昨天 + `usage.range(7)`），主人端首屏约 2–4s（含小狗端往返）。后续可考虑服务端缓存。

## 待办
- 真机（非模拟器）复测冷启动、使用时长页首屏耗时。
- 规则数量增长（>50）时 `AppLimitWatcher.parseRules` 的成本需再测。
